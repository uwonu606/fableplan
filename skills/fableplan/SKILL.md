# fableplan 워크플로

opusplan(플랜=Opus, 구현=Sonnet)과 같은 구조를 "플랜=현재 세션 모델(Fable), 구현=Opus"로 수행한다.
플랜 품질은 메인 스레드 모델이, 구현은 `opus-builder` agent가 담당한다.

작업 설명: $ARGUMENTS

## 절차

0. **세션 모델 확인**
   - 이 skill은 세션 모델을 바꿀 수 없다. 플랜은 지금 이 대화를 돌리고 있는 모델이 작성한다.
   - 현재 세션 모델이 Fable이 아니면 조용히 넘어가지 말고 사용자에게 알린다: 지금 세션 모델이 무엇인지, 그래서 플랜을 누가 작성하게 되는지.
   - `AskUserQuestion`으로 물어본다 — (a) 이대로 진행, (b) 중단하고 `/model fable` 로 바꾼 뒤 다시 실행. 답을 받고 나서 1단계로 넘어간다.
   - 세션 모델이 Fable이면 이 단계는 아무 출력 없이 건너뛴다.

1. **플랜 단계 (현재 세션 모델)**
   - 작업 설명이 비어 있으면 사용자에게 무엇을 만들지 물어본다.
   - plan mode가 아니면 `EnterPlanMode`를 호출해 plan mode로 진입한다.
   - 코드베이스를 탐색하고 구현 플랜을 작성한다. 플랜에는 반드시 포함:
     - 변경/생성할 파일 목록과 각 파일에서 할 일
     - 재사용할 기존 함수/유틸 (파일 경로 포함)
     - 검증 방법 (실행할 테스트/빌드/커맨드)
   - `ExitPlanMode`로 사용자 승인을 요청한다.
   - 거부되면 피드백을 반영해 플랜을 수정하고 다시 승인을 요청한다.

2. **구현 단계 (Opus subagent)**
   - 플랜이 승인되면 즉시 `opus-builder` agent를 실행한다:
     - Agent tool, `subagent_type: "opus-builder"`, `run_in_background: false`
     - 프롬프트에 다음을 전부 담는다: 승인된 플랜 전문(요약 금지), 작업 디렉토리 절대 경로, 플랜 단계에서 알아낸 핵심 컨텍스트(관련 파일 경로, 재사용할 코드 위치, 주의사항)
   - subagent는 사용자에게 질문할 수 없으므로, 프롬프트에 모호함이 남지 않게 전달한다. 플랜에 없는 결정사항이 남아 있다면 agent 실행 전에 사용자에게 먼저 확인한다.
   - 구현 자체를 메인 스레드에서 직접 수행하지 않는다. 구현은 opus-builder의 몫이다.

3. **검증·보고 단계 (현재 세션 모델)**
   - agent가 반환한 변경 파일 목록과 테스트 결과를 확인한다.
   - 플랜의 검증 절차를 메인 스레드에서 직접 재실행한다 (테스트/빌드/실행).
   - 실패가 있으면: 실패 내용을 정리해 `opus-builder`에게 수정 작업으로 다시 위임한다 (SendMessage로 기존 agent를 잇거나 새로 실행).
   - 최종 보고: 무엇이 바뀌었고, 검증이 어떻게 통과했는지 사용자에게 요약한다.

## 규칙

- 플랜 승인 전에는 어떤 파일도 수정하지 않는다. 단, plan mode가 하드 차단하는 것은 Edit/Write뿐이다 — 변경성 Bash(rm, git commit 등)는 차단이 아니라 사용자 승인 프롬프트로 넘어가므로 승인되면 실행될 수 있다. 그래도 이 워크플로에서는 승인 전에 변경성 Bash를 호출하지 않는다. 플랜 작성에 변경 실험이 꼭 필요하면 AskUserQuestion으로 사용자에게 먼저 확인한다.
- opus-builder에게 플랜을 넘길 때 축약하지 않는다 — 승인된 플랜 원문 그대로.
- opus-builder가 플랜 범위를 벗어난 변경을 보고하면, 사용자에게 알리고 되돌릴지 확인한다.
